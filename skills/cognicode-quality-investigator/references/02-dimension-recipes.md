# Playbook de extracción por dimensión: pregunta → evidencia → contraste

No conviertas una tool en un veredicto. Primero comprueba el catálogo real (`tools/list`), el workspace/capacidad, el estado del índice y el alcance. Todos los nombres son **candidatos** hasta que el binario instalado confirme el schema. Distingue grafo de llamadas, grafo de imports/dependencias, flujo de datos, datos de CI y trazas runtime: responden preguntas diferentes.

| Dimensión | Pregunta y extracción CogniCode (si está disponible) | Contraste independiente y falsos positivos | Evidencia mínima para sostener la conclusión |
|---|---|---|---|
| D01 Arquitectura y hexagonal | `explorer_query_moldql`/`detect_architecture_drift`/`impact_detect_cycles` para candidatos; `get_file_symbols`, `find_usages`, `go_to_definition`, `get_call_hierarchy` y `trace_path` para vías reales entre capas. `check_architecture`/`get_imports` solo si tools/list los anuncia. | Contrastar reglas **declaradas por el proyecto** con import DAG, build/manifest, DI/wiring, codegen, reflection y runtime; ciclo de llamadas ≠ ciclo de dependencias de módulos. Una dependencia via port no es infracción per se. | Regla/ADR vigente + origen y destino identificados + vínculo observado + contexto/contratos + alcance de búsqueda. |
| D02 SOLID y tipado funcional | `get_file_symbols`, `get_symbol_code`, `find_references`, `find_usages`, `get_call_hierarchy`, `get_complexity` (pista). `solid_audit` solo si lo expone el servidor real. Identificar interfaces, implementaciones, jerarquías, estados/error APIs. | Contratos tipados, caller real, tests de sustitución y compilación; una clase grande o un constructor largo es candidato, no SRP/DIP/LSP violado. ADT/funciones puras solo exigibles si están adoptados o hay fallo real. | Par de consumidor/proveedor y razón concreta del incumplimiento, ejemplo mínimo verificable. |
| D03 Connascence estática | Símbolos y usos vinculados a tipos, parámetros, nombre, significado, orden y algoritmos: `get_symbol_code`, `find_references`, `get_call_hierarchy`, `go_to_definition` y datos de cambios si autorizados. | Comprobar si **dos elementos deben cambiar juntos** (no solo similitud/co-change). Para posición: misma llamada/codec y pruebas de reordenación; para significado: magic constants compartidas; para algoritmo: divergencia semántica de dos implementaciones. Análisis SCIJ requiere definición y herramienta validada en Java; no extrapolar. | Identidades del par + contrato que induce cambio conjunto + prueba de ruptura o cambio conjunto controlado; sin índice inventado. |
| D04 Duplicidad, cohesión, acoplamiento, complejidad | `get_complexity`, `graph_communities`, `graph_surprising_connections`, `graph_god_nodes`, `graph_explain`, `get_call_hierarchy`, `get_file_symbols`. | Duplicados: comparar AST/cuerpo y semántica, no solo nombres. Comunidad PageRank/fan-in ≠ responsabilidad o cohesión; centralidad puede ser diseño intencional. Validar complejidad si parser pudo fallar. | Fragmentos o rutas de cambio obligadas, test que reproduzca divergencia/efecto; métricas con definición/denominador. |
| D05 Deuda técnica y evolución | `analyze_impact`, `impact_radius`, `graph_explain` sobre módulos de deuda, `detect_architecture_drift` solo para cambios con baseline comparable. | Issue/ADR/work journal, fecha, commit de introducción, diff a HEAD, consumidores y razón de diferimiento. No reinterpretar hallazgos históricos como regresión reciente. | Referencia deuda + estado vigente + superficie en SHA actual + riesgo diferenciado de preferencia de diseño. |
| D06 Tests y cobertura | `analyze_impact`/`find_usages` para seleccionar rutas afectadas; `get_entry_points`/`trace_path` para localizar entradas de prueba; `find_quality_issues` para hallazgos de calidad **ya ingestados**. | Ejecutar tests reales permitidos, registrar JUnit/coverage/mutation/contract tests con SHA; revisar asserts, fixtures y flaky; grafo no mide cobertura de líneas/ramas ni certifica tests por sí mismo. | Comando o job real, exit, casos y artefacto de cobertura, denominador e instrumentación del SHA. |
| D07 CI/CD | `analyze_impact` para decidir suites focales; `search_content`/`read_file` para manifests y workflows; `detect_architecture_drift` en archivos de CI solo si soporte demostrado. | API de CI del **SHA actual**, jobs realmente ejecutados, matrices/paths/timeouts, logs completos; pipeline YAML presente ≠ verde. Distinguir cancelación y timeout de PASS. | Run URL/id, head SHA, status por job, comandos y artefactos de validación. |
| D08 Seguridad | `get_entry_points`, `trace_path`, `find_usages`, `get_symbol_code`, `search_content`; `taint_flow`/análisis DFG solo si runtime expone y certifica soporte; investigar fuente → validación/sanitización → sumidero. | SAST/secret scanning/SBOM, pruebas de ataque controladas y versión/config real. Rutas potenciales o substring `eval` ≠ vulnerabilidad explotable; resultados incompletos se etiquetan hipótesis. | Ubicación source+sink, tipo de flujo y sanitizadores inspeccionados, límite de precisión, impacto y evidencia de ejecución si se afirma explotación. |
| D09 Rendimiento | `get_hot_paths`/`graph_pagerank`/`graph_god_nodes` para candidatos estructurales; `get_complexity` para coste algorítmico aparente. | Benchmark/replay/profiling/traza del workload real bajo configuración y hardware fijados; fan-in estático ≠ tiempo ni llamadas reales; repetir y reportar dispersión. | Baseline y candidato, dataset, entorno, número repeticiones, métricas p50/p95 o perfil observado, no estimaciones de centralidad. |
| D10 Dependencias/licencias | `read_file`/`search_content` de manifests/lockfiles, `get_file_symbols` y trazado de usos para dependencia realmente alcanzable. | Gestor de paquetes/lock, SBOM+scanner de vulnerabilidades, licencia oficial y contexto de distribución; un import no prueba versión ni CVE aplicable. | Paquete+versión exacta+fuente de advisory+condición afectada+uso/alcance o reporte SBOM enlazado. |
| D11 Documentación y mantenibilidad | `search_content`/`read_file`, `get_symbol_code`, navegación a implementación; `detect_architecture_drift` solo sobre contrato adecuado. | Comparar ADR/README/AGENTS con código y tests del SHA. Distinguir doc histórica, decisión vigente y comentario desfasado; claridad es juicio contextual, no algoritmo. | Afirmación documental concreta, prueba contradicción (código o ejecución) y versión/fecha. |
| D12 Observabilidad | `get_entry_points`, `trace_path`, `find_usages`, `search_content` para emisión de evento/span/métrica y su consumidor. | Ejecutar escenario de extremo a extremo si autorizado: trace id propagado, etiquetas sin secretos, duración, log visible y fallos; mera dependencia OpenTelemetry o string `tracing` ≠ señal efectiva. | Flujo productor→exportador→backend/lector con resultado observable o declarar instrumentación documental/no verificada. |

## Composiciones útiles de investigación

- **Arquitectura**: `get_file_symbols` → localizar port/adapter → `find_usages` + `go_to_definition` → `trace_path` (si grafo completo) → consultar dependencias de build → prueba arquitectónica real. Si el camino pasa por interfaz y el binding es runtime, documentar ambos.
- **Impacto de un cambio**: diff real y SHA → `analyze_impact` → `get_call_hierarchy` sobre afectados → inspeccionar consumidores concretos → selección de tests → ejecución focal → registrar `NOT_RUN` para integrales pendientes.
- **Seguridad**: source/sink detectados → grafo de llamadas acotado → inspección de validación/sanitizador → taint certificado o prueba mínima segura; sin path completo no elevar una sospecha a vulnerabilidad confirmada.
- **Deuda**: comparar el mismo conjunto de fuentes sobre dos commits, con `schema_digest`/herramienta idénticos; registrar hallazgos nuevos, resueltos, reubicados, ambigüos y no reanalizados. El cambio de número de incidencias no es automáticamente mejora/empeoramiento.

## Selección de pruebas por riesgo

Una auditoría en desarrollo puede centrarse en rutas modificadas y dependencias demostradas; una auditoría de integración o release debe usar los gates del repositorio en el SHA nuevo. El grafo ayuda a **proponer** la selección de tests, nunca a demostrar por sí solo su suficiencia, especialmente cuando hay reflexión, plugins, eventos, código generado o consumo remoto.
