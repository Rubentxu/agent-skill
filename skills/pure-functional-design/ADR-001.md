# ADR-001 — Skill router único con lentes de método y perfiles idiomáticos

**Estado:** propuesto · **Fecha:** 2026-10-27

## Contexto

Queremos trasladar Haskell FP (semántica, ADTs, álgebra, pureza, modelado de dominio) a Rust/Kotlin sin crear implementaciones exóticas ni obligar a descargar todo el material de un agente en cada tarea. La skill `delivery-first-testing` ya usa router + lens registry + affordances HATEOAS-like; replicar el patrón reduce aprendizaje y riesgos.

## Decisión

Una skill instalable `pure-functional-design` con: un router portable, lentes metodológicas centradas en preguntas, perfiles idiomáticos separados por lenguaje, catálogo `ready/planned`, scripts puros opcionales y evals adversariales. Las lentes contienen procedimientos autónomos de decisión, **no** motores de análisis ni comandos implícitos. No hay código de escritura/ejecución de proyectos en el selector.

`delivery-first-testing` mantiene la responsabilidad de ejecución de tests y política de conservación; `cognicode-diagrams` conserva propiedad de descubrimiento de símbolos/grafo bajo sus precondiciones. La skill puede funcionar manualmente si ninguno está instalado.

## Consecuencias

- Positivas: reutilización sin duplicidad, costes de contexto bajos, perfil Rust/Kotlin reemplazable, rutas de auditoría reales.
- Negativas: la aplicación requiere disciplina humana del agente; los playbooks no prueban automáticamente arquitectura ni garantizan dominio correcto.
- Riesgos: router basado solo en señales reportadas puede subestimar complejidad; el estado `unknown/stale` debe detener recomendaciones presentadas como hallazgos.

## Alternativas descartadas

1. Una skill independiente por cada patrón: alto solapamiento y conflictos de autoridad.
2. Un motor de FP con DSL/HKT para todos los lenguajes: Haskell impuesto artificialmente y elevado mantenimiento.
3. Reemplazar Arrow/kotlinx/Rust std por una librería propia: sin necesidad ni evidencia.
4. Confiar en documentos de roadmap como prueba de implementación: fomenta falsas conclusiones.

## Reevaluación

Separar `domain-ontology-discovery` como skill autónoma solo si se comprueba utilidad independiente para varios lenguajes y herramientas; separar `functional-architecture-refactor` si requiere workflow/evidencias distintas de `pure-functional-design`, no por crecimiento del número de Markdown.
