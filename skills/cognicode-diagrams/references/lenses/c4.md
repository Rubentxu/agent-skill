# Lente C4 — arquitectura implementada, solo CogniCode

La única fuente arquitectónica es el **análisis de código a través de CogniCode CLI/MCP**. No leer directamente código, manifiestos, Terraform, Dockerfiles, configuraciones, tests, ADR o documentación; tampoco tomarlos como evidencia si el buscador de CogniCode los devuelve. [Contrato](../investigation-contract.md).

## Preguntas activas

- **C1**: ¿qué frontera del sistema y qué actores/sistemas externos están demostrados por rutas de código, superficies públicas o interacciones implementadas? Si los actores no pueden derivarse, etiquetarlos `UNKNOWN`, no inventarlos.
- **C2**: ¿qué unidades ejecutables separadas y stores existen realmente? Usar consultas sucesivas de CogniCode a entradas ejecutables, bootstrap, inicialización de servicios, conexiones y llamadas. Una carpeta, crate o dependencia **no** es un contenedor.
- **C3**: ¿qué componentes colaboran dentro de una unidad demostrada? Investigar servicios/handlers/repositorios, sus símbolos y aristas, y pedir a CogniCode fragmentos relevantes de **cada extremo**.
- **Dinámico/despliegue**: solo cuando CogniCode presente evidencia de ese plano; `calls`/`imports` no demuestran procesos, protocolo, orden temporal ni topología de deployment.

## Bucle de profundización

Primero consultar panorama, después subgrafos/símbolos concretos, y finalmente código contextual devuelto por CogniCode para contrastar cada afirmación. Si se pide zoom C3 o «más detalle», **añadir consultas** enfocadas. Ante ambigüedades, reconsultar; si CogniCode no puede resolverlas, registrar `PARTIAL/UNKNOWN` sin otras herramientas.

## Modelo y resultados

Cada componente y relación lleva `claim_id`, `query_id`, símbolos, código de referencia cuando se facilite y `plane` (`static|runtime|deployment`). Una inferencia se declara, nunca se dibuja como hecho corroborado. Generar Mermaid C4, Structurizr o LikeC4 desde ese modelo; validar formato, semántica y fidelidad **por separado**. Un diagrama anterior es material editable/curado, no evidencia.

Véanse [evidence.md](../evidence.md), [scan.md](../scan.md) y los formatos registrados.

## Legibilidad y alcance obligatorio

Por defecto, **máximo 15 nodos por vista** (máximo absoluto configurable 20). Si el modelo tiene 29, dividir en varias vistas por contenedor/rol, con panorama C2 y C3 acotados; no comprimir letras ni esconder nodos/relaciones sin documentarlo. Registrar `research.view.node_count` y `max_nodes`; el router ofrece `split-view` si excede. No confundir legibilidad con evidencia. Para Kotlin comprobar el registro instalado **antes** de prometer C4 global; un uso/ref Java o Kotlin no se convierte automáticamente en arista de call graph (ver [referencias](../evidence-reference-links.md)).

## Metadatos visuales

Cuando el formato lo soporte, transportar `claim_id`, `query_id`, `coverage` y `plane` en el elemento/relación. Los atributos de conexión se obtienen de CogniCode; tecnología, protocolo y orden no se infieren. Una vista dinámica necesita pasos corroborados y etiqueta «flujo declarado», no runtime observado. Las categorías del atlas son optativas por pregunta. [Reglas](../visual-evidence.md).

## La vista derivada, que es dato

La selección es curada y la vista es derivada: un proyector lee el ledger y publica la vista como dato, con cada elemento y cada relación trazados a sus afirmaciones. Nada de la vista se escribe a mano, y nada de ella se dibuja: cualquier producto que quiera pintarla la traduce a sus propias formas.

```text
python3 scripts/c4_view.py --repo <raíz> --view containers        # deriva y publica el resultado
python3 scripts/c4_view.py --repo <raíz> --view containers --emit # además lo deja en lenses/c4/views/
```

La selección vive en `lenses/c4/reports/<vista>.atlas.json`: qué afirmaciones forman la vista, qué pregunta de la lente responde (`C1|C2|C3`) y qué clase C4 tiene cada elemento (`system|external_system|container|component|store`). La clase vive en la selección, no en la afirmación: el mismo símbolo puede ser contenedor en una vista y componente en otra, y la afirmación sigue siendo solo «entidad corroborada».

Este es el ejemplo canónico, sobre el ledger canónico de [evidencia](../evidence.md). Las pruebas lo ejecutan: si el ejemplo y el proyector dejan de coincidir, la suite falla.

```json seleccion
{
  "schema_version": 1,
  "lens": "c4",
  "question": "C3",
  "label": "Entrada y almacenamiento",
  "claim_ids": ["C-1", "R-1", "R-2"],
  "kinds": { "C-1": "component" }
}
```

```json vista
{
  "schema_version": 1,
  "generator": "cognicode-diagrams-c4-view",
  "lens": "c4",
  "view": "ejemplo",
  "question": "C3",
  "label": "Entrada y almacenamiento",
  "basis": { "identity": null, "status": "unknown", "revision": "rev-abc123" },
  "elements": [
    { "id": "App::Entry", "kind": "component", "label": "App::Entry",
      "claim_ids": ["C-1"], "coverage": "complete",
      "location": { "path": "src/entry.rs", "line": 10 } }
  ],
  "relations": [],
  "holes": [
    { "claim_id": "R-1", "reason": "un extremo no esta en la vista: App::Store" },
    { "claim_id": "R-2", "reason": "una referencia localizada no es una arista del grafo" }
  ],
  "counts": { "elements": 1, "relations": 0, "holes": 2 },
  "status": "partial"
}
```

Las reglas del proyector:

- **Un elemento** es una afirmación de entidad `OBSERVED_CODE` corroborada; su identidad es el `symbol_id` (estable entre vistas) y las afirmaciones que lo corroboran se agrupan en él. Su sitio sale de los `symbol_locations` de las consultas que lo corroboran.
- **Una relación** es una afirmación `graph_edge` corroborada, con el `relation_id` que devolvió el grafo. Una `reference_link` nunca es una arista, y una relación cuyo extremo no está seleccionado es un hueco, no una arista recortada.
- **Un hueco** es una afirmación de la selección que no llegó: no corroborada, de intención, referencia, extremo ausente, clase sin declarar. Se publica con su motivo, porque un hueco con su motivo es información y una omisión silenciosa no.
- **La base** la declaran las consultas que sostienen lo publicado, con las mismas reglas del brief: identidad solo si todas la declaran igual, revisión solo si todas declaran la misma.
- **`inputs`** lleva las sumas del material del que derivó, para que quien lea la vista sepa de qué ledger habla.
- **El presupuesto de legibilidad se exige**: más de 15 elementos y la vista se divide, no se aprieta.
